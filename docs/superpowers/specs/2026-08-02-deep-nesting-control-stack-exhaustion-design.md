# 深いネストによる制御スタック枯渇と接続ハングの修正: 設計

- 日付: 2026-08-02
- ステータス: 設計承認済み（実装未着手）
- 分岐元: `main`（`6033668`）
- 対象所見: 2026-08-01 監査の Critical 1 件（`docs/plans/2026-08-01-audit-edge-cases.md` 所見1）

## 1. 背景

2026-08-01 のロバスト性監査で唯一の Critical。**構文的に完全に正しい、ただ深くネストしただけの
Lisp フォーム**（深さ 20,000）を `lisp-read-file`（既定 collapsed モード）または
`lisp-check-parens` に渡すと、SBCL の制御スタックが枯渇し、その要求を処理していた接続スレッドが
デバッガ起動状態のまま**永久に停止**する。

独立検証で再現済み。90 秒待っても応答が一切返らず、最初の監査が作った 2 本のスレッドが
**9 分以上経過後も生存**していた。サーバプロセス全体は生きたまま新規接続を受け付け続けるため、
**この経路を叩くたびに気づかれないままスレッドが 1 本ずつ積み上がる**。サーバが止まらない分、
かえって見逃されやすい。

後片付けでプローブ用インスタンスが SIGTERM で終了せず SIGKILL を要したことも、
停止したスレッドが残っていたことと整合する。

## 2. 現状の実測（再調査不要）

| 事実 | 根拠 |
|------|------|
| `sb-ext:disable-debugger` はワーカー子プロセスでしか呼ばれていない | `src/worker/main.lisp:188` のみ |
| `lisp-read-file` / `lisp-check-parens` は親プロセスで動く | CLAUDE.md のツール配置表 |
| 本番の起動経路は `cl-mcp:run` | `README.md:54,132,152` |
| **テストも同じ `run` と `serve-tcp` を呼ぶ** | `tests/core-test.lisp:25,38`、`tests/tcp-test.lisp:35`、`tests/bridge-test.lisp:20` |
| 文字列・行コメント・ネストしたブロックコメントを正しく扱う文字レベルスキャナが既にある | `src/validate.lisp:128` `%scan-parens`。開き括弧のスタックを保持しており、深さはその長さ |
| このリポジトリ 123 ファイルの最大ネスト深さは **20** | `src/proxy.lisp`、`src/pool.lisp` |
| 過大入力は例外ではなく構造化結果で返す慣習がある | `src/validate.lisp:295` の `"kind": "too-large"` |
| `cst.lisp` と `validate.lisp` は相互に独立 | 双方の `defpackage` を確認済み |

### 2.1 このリポジトリは同じ問題を一度解いている

`src/macroexpand-core.lisp:50-54` が実測に基づいてこう記録している。

> exhaustion is *fatal*: at a 2 MB control stack SBCL dies at roughly 5,800 expansions with
> `Control stack exhausted' and no condition is signalled at all, because the fault lands inside
> a pseudo-atomic allocation. The STORAGE-CONDITION clause ... cannot catch that;
> **only never reaching it works.**

コミット `d140ea4` がその結論を実装している（`*max-walk-expansions*` = 1000、実コストは通常の
`defun` で 14）。**本設計はこの先例に従う。** ただし今回の監査ではデバッガが起動している、
つまり condition は signal されており、マクロ展開のケースとは挙動が異なる。
したがって「捕捉に頼らない」方針は維持しつつ、デバッガ経路も別途塞ぐ。

## 3. 修正は 2 層に分かれる

問題は 1 つに見えて 2 つある。

| # | 問題 | 効果 |
|---|------|------|
| 1 | 接続処理スレッドがデバッガに入って永久停止する | 深いネストに限らず、**親側ツールで未処理のシリアス condition が起きればどれでも**同じことが起きる |
| 2 | リーダーが深さを制限せず再帰する | 到達すれば制御スタックを枯渇させる |

1 だけを直しても「永久ハング＋スレッドリーク」は消えるが、利用者には原因の分からない切断が返る。
2 だけを直してもこの経路は守れるが、他の未処理 condition では依然スレッドが永久停止する。
**両方直す。**

## 4. 修正 1: 接続スレッドをデバッガに入れない

### 4.1 グローバルな `disable-debugger` は採らない

`cl-mcp:run` は本番の入口であると同時に**テストが呼ぶ関数でもある**（§2）。そこで
`(sb-ext:disable-debugger)` を呼ぶとテスト実行中もデバッガが無効化され、rove の異常報告が変わる。
REPL に cl-mcp をロードして使う開発者にも影響する。

### 4.2 接続処理スレッドに閉じる

各接続を処理するスレッドで `sb-ext:*invoke-debugger-hook*` を束縛し、デバッガに入る代わりに
**ログを出してその接続だけを畳む**。

この形を選ぶ理由:

- **スコープが危険の所在と正確に一致する。** サーバが処理する要求の中でデバッガに入ることは
  常に誤りである一方、REPL やテストでデバッガに入ることは正しい
- **condition の型に依存しない。** デバッガに入るものは何であれ捕まる。§2.1 の
  「condition が上がらないこともある」という実測と衝突しない
- テストと REPL のデバッガ体験を壊さない

対象は 3 経路:

| 経路 | ファイル |
|------|---------|
| TCP 接続スレッド | `src/tcp.lisp` |
| HTTP ハンドラスレッド | `src/http.lisp` |
| stdio ループ | `src/run.lisp` |

フックはログを出したうえでスタックを巻き戻す。**プロセスは落とさない** — 他のセッションの
接続を巻き添えにしないため。

**巻き戻し先を用意することが実装の要である。** `*invoke-debugger-hook*` に束縛した関数は、
呼ばれた地点から**非局所脱出しなければ、戻った先で結局デバッガに入る**。したがって接続ハンドラ側に
脱出先（`catch` タグ、あるいは `abort` リスタート）を確立し、フックはそこへ脱出する。
「ログを出して return する」だけの実装は、症状を変えずログだけ増やす。テスト 5 はこの区別を
検出できるものでなければならない。

## 5. 修正 2: ネスト深さの上限

### 5.1 守るべき経路は 2 つ

| 経路 | 入口 | 対象ツール |
|------|------|-----------|
| CST | `src/cst.lisp:256` `parse-top-level-forms` | `lisp-read-file`、`lisp-edit-form`、`lisp-patch-form` |
| 標準リーダー | `src/validate.lisp:208` `%try-reader-check` | `lisp-check-parens` |

### 5.2 既存スキャナを `src/utils/` に降ろす

深さの判定には `%scan-parens`（`src/validate.lisp:128`）を使う。素朴な括弧カウントでは
`"((((("` のような文字列リテラルを含む**正当なファイルを誤って弾く**ため、文字列・コメントを
正しく扱う既存スキャナに意味がある。

`validate.lisp` は `fs` と `tools/*` に依存するツール層のモジュールなので、低レベルの
`cst.lisp` から参照させたくない。**スキャナとその補助関数を `src/utils/` の新モジュールに移し、
`validate` と `cst` の双方から import する。** Lisp テキストの汎用スキャナは本来 `validate`
固有のものではない。

**移動は挙動を変えない移動に限る。** `%scan-parens` は `src/validate.lisp` の中核で、
同ファイルは式カバレッジ 85.5% と手厚くテストされている。移動後も既存テストが全て緑であることを
もって等価性を確認する。

### 5.3 上限値は推測せず測ってから決める

実コードの最大が 20、監査で致命的だったのが 20,000。**その間のどこで実際に破綻するかは未測定である。**

**隔離プロセスで実際の破綻深度を二分探索し、その十分下に上限を置く。** `*max-walk-expansions*`
が「1000 は致命的深度のはるか下、実コードのはるか上」という実測付きの根拠を持つのと同じ形にする。
1,000 が有力だが、測定結果が決める。

測定は必ず別プロセスで行う。破綻すればそのプロセスは落ちるが、それは想定内であり、
セッションを巻き込まない。

### 5.4 拒否の返し方は経路ごとに既存慣習へ合わせる

| 経路 | 返し方 |
|------|-------|
| `lisp-check-parens` | `too-large` と同じ構造化結果（`"ok": nil, "kind": "too-deep"`）。**上限値と実際の深さを含める** |
| CST 経路 | 上限を名指しした条件を signal し、ツール層が JSON-RPC エラーに変換する |

どちらの経路でも、利用者が「何が起きたのか」「どうすればよいのか」を読み取れるメッセージにする。
原因の分からない切断は Major 相当の欠陥である。

## 6. テスト戦略

| # | 検証内容 | 目的 |
|---|---------|------|
| 1 | 上限ちょうどの深さは通り、上限＋1 は拒否される | 境界 |
| 2 | **文字列リテラル内の括弧が深さに数えられない** | 素朴なカウンタなら誤って正当なファイルを弾く箇所 |
| 3 | 監査の再現手順（深さ 20,000）が、`lisp-read-file` / `lisp-check-parens` / `lisp-edit-form` / `lisp-patch-form` の **4 ツールすべて**でハングせずエラーを返す | 所見そのものの回帰防止。監査時に未確認だった 2 ツール（§8）もここで確定させる |
| 4 | `src/proxy.lisp`（実測深さ 20）が従来どおり読める | 実コードの回帰防止 |
| 5 | 接続スレッドで未処理のシリアス condition が起きたとき、スレッドがデバッガに入らず接続だけが畳まれ、**サーバは他の接続を処理し続ける** | 修正 1 |

テスト 3 と 5 は所見の中身そのものなので、**片方でも欠ければこのブランチは目的を達していない。**

テスト 5 は制御スタック枯渇そのものを起こす必要はない。デバッガに入る条件を意図的に signal すれば
同じ経路を通る。実際のスタック枯渇をテストスイートに入れるのは、プロセスを落とすリスクに見合わない。

## 7. リスク

| リスク | 扱い |
|--------|------|
| `%scan-parens` の移動が挙動を変える | 移動のみで内容を変えない。既存テストが全て緑であることを等価性の根拠とする |
| 上限が実コードを弾く | 実測最大 20 に対し十分な余裕を取る。テスト 4 で実ファイルの回帰を防ぐ |
| 上限が破綻深度に届いてしまう | §5.3 の測定で破綻深度を先に確定させる。推測値は使わない |
| `*invoke-debugger-hook*` の束縛漏れ | 3 経路すべてにテストを置く。1 経路だけ直すと、そこだけ安全という誤解を生む |
| デバッガフックがテスト実行に影響する | 束縛はスレッドローカル。テストが `run` / `serve-tcp` を呼ぶ既存経路が緑のままであることを確認する |

## 8. スコープ外

- **他の 11 件の所見**（Major 7 / Minor 4）。本ブランチは Critical 1 件のみを扱う
- `lisp-edit-form` / `lisp-patch-form` に深いネストを投げた場合の挙動の実測。監査時はスレッドリークを
  増やさないため未実施だった。同じ CST 経路を通るので修正 2 で同時に守られるが、**そのことの確認は
  テスト 3 の対象に含める**
- カバレッジ計測基盤（PR #133）との統合。本ブランチは `main` から分岐しており、独立している
- ワーカー子プロセス側の同種の問題。ワーカーは既に `disable-debugger` 済みで、症状が異なる
