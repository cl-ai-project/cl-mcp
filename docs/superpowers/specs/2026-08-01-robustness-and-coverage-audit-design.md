# cl-mcp のロバスト性・テスト網羅性の広範な検証: 設計

- 日付: 2026-08-01
- ステータス: 設計承認済み（実装未着手）
- 対象コミット: `6033668`
- 想定受益者: cl-mcp のメンテナ

## 1. 背景と問い

cl-mcp には `comprehensive-test` と `dogfooding-cl-mcp` という探索的な検証スキルがあり、
`docs/plans/` には 2026-03 以降の監査記録が 30 本近く蓄積している。一方で
**テスト網羅性を客観的な数値として測ったことは一度もない**（`sb-cover` の痕跡はリポジトリ内に皆無）。

その結果、監査のたびに掘られる場所が同じ領域（clgrep、macroexpand、scaffold）に偏り、
**一度もテストが通っていない領域があるとしても、それに気づく手段がない**。

本設計は「カバレッジを実測する基盤」と「その数値を入力とするロバスト性監査」を作る。

## 2. 現状の実測

### 2.1 テストスイートのベースライン

`rove cl-mcp.asd` をクリーンプロセスで実行（2026-08-01、コミット `6033668`）:

| 項目 | 値 |
|------|-----|
| 成功アサーション | 3,548 |
| 実質的な失敗 | 0 |
| 終了コード | 0 |
| 所要時間 | 353.25 秒 |
| 最大 RSS | 593,148 kB |
| src | 59 ファイル / 18,225 行 |
| tests | 65 ファイル / 18,800 行 |

ログ中に `× 1 of 1 test failed` が 1 件現れるが、これは `project-scaffold` の
テストが「わざと落ちるプロジェクト（`rove-red`）を生成し、`test-op` が
ちゃんと失敗を報告することを検証する」意図的なフィクスチャである。実害はないが、
**ログを読んだ人間・エージェントが本物の失敗と誤読しやすい**。監査の所見候補として記録する。

### 2.2 sb-cover の実現可能性（検証済み）

`src/utils/strings.lisp` だけを計装して `cl-mcp/tests/utils-strings-test` を実行したところ、
HTML レポートが生成され **式カバレッジ 21/21 (100.0%)、分岐カバレッジ 4/4 (100.0%)** を得た。
ASDF の package-inferred-system 構成とも衝突しない。

副次的に判明した制約: **sb-cover の出力は HTML のみで、機械可読なテキストサマリを出さない。**

### 2.3 ワーカーはプロセス境界の向こう側にある

ワーカーは `sb-ext:run-program` により別の SBCL 子プロセスとして起動される
（`src/worker-client.lisp:314`）。`sb-cover` は自プロセス内の実行しか計測できないため、
`pool-test` や `worker-test` がワーカー経由で叩いたコードは素直に測ると「未カバー」に見える。

ただしワーカー側ロジックは `repl-core` / `code-core` / `system-loader-core` /
`test-runner-core` / `macroexpand-core` に分離済みで、`src/worker/handlers.lisp` は
それらへの薄いディスパッチャである。したがって真にワーカー専用なのは
`src/worker/` 配下のプロセス制御コードに限られる見込みである（正確な範囲は §6 で確定させる）。

### 2.4 `docs/plans/` は追跡対象外

`.gitignore` に `docs/plans/` が含まれる。過去の監査記録が全てそこにあるのは、
この repo が「エージェントの作業文書はコミットしない」方針を取っているためと読める。
**カバレッジ数値の推移を git で追いたいなら、サマリは別の場所に置く必要がある。**

## 3. 決定事項

ブレインストーミングで確定した方針:

| 論点 | 決定 |
|------|------|
| 成果物 | 計測基盤 ＋ 監査レポート（一度きりの監査で終わらせない） |
| カバレッジ計測範囲 | 親プロセスのみ。ワーカー内の実行は測らず、盲点として明示列挙する |
| ロバスト性監査の観点 | 「障害回復・プロセス境界」と「異常入力・境界値」の 2 つ |
| 自動化の範囲 | ローカル実行スクリプトのみ。CI には載せない |
| 監査の実施方法 | 既存の `comprehensive-test` スキル（観点別並列エージェント） |
| 実施順序 | 計測を先に完了させ、その数値を監査エージェントへの入力にする |

**実施順序を直列にした理由**: エージェントが「どこを探すべきか」を数値で知った状態で
走らないと、既に手厚くテストされた領域を再検証しがちになる。過去の監査記録が
同じ領域に偏っているのは、まさにこの情報がなかったためと考えられる。

## 4. アーキテクチャ

4 つの部品に分け、依存を一方向に保つ。

| # | 部品 | 唯一の責務 | 入力 | 出力 |
|---|------|-----------|------|------|
| 1 | 計測ドライバ `scripts/coverage.ros` | src を計装して全スイートを回し、カバレッジデータを出す | なし | HTML 一式 ＋ ファイル別カバレッジ率のテキスト |
| 2 | 分類テーブル `scripts/coverage-scope.md` | src の各ファイルを「親で実行 / ワーカー専用 / 計測不能」に分類し、理由を 1 行ずつ添える | src の構成（静的） | 盲点リスト |
| 3 | 監査実行 | `comprehensive-test` を 2 観点で起動 | 1 と 2 の出力 | 観点別の所見 |
| 4 | 統合レポート | 人間が読む唯一の成果物 | 1〜3 すべて | 優先度付き所見リスト |

**この分け方の狙い**は、部品 1 が「数値を出す」以外を一切やらないことにある。
レポートの書式や監査の観点が変わっても計測ドライバは触らずに済む。
部品 2 は部品 1 の出力に依存しない静的な事実なので、計測が失敗しても盲点の一覧だけは残る。

部品 2 をスクリプト内の定数ではなく独立した Markdown にするのは、
「これは本当に計測不能か」を人間が読んで検証できるようにするためである。

### 4.1 成果物の置き場所

| 成果物 | 置き場所 | git |
|--------|---------|-----|
| HTML レポート | `coverage/` | 追跡しない（`.gitignore` に追加）。src 18,000 行分で数 MB になる |
| カバレッジのテキストサマリ | `docs/coverage-summary.md` | **追跡する**。推移が見えることが計測基盤の価値の半分であるため |
| 分類テーブル | `scripts/coverage-scope.md` | 追跡する |
| 計測ドライバ | `scripts/coverage.ros` | 追跡する |
| 統合監査レポート | `docs/plans/2026-08-01-robustness-and-coverage-audit.md` | 追跡しない（repo の既存方針に従う作業文書） |

## 5. 部品 1: 計測ドライバ `scripts/coverage.ros`

### 5.1 実行手順

1. `(require :sb-cover)` → 計装 ON
2. `(asdf:load-system :cl-mcp :force t)` で **src だけ**を計装済みで再コンパイル
3. 計装 OFF に戻す
4. テストシステムを **`:force` なしで**ロードする（**`tests/` は計装しない**。テストコード自身の
   カバレッジは数値を汚すだけである。ここで force すると src が計装なしで再コンパイルされ、
   手順 2 が無駄になる）
5. 全テストパッケージを rove で実行。パッケージ一覧は `tests.lisp` の `test-op` フックと同じ方法
   （`asdf:system-depends-on` から `cl-mcp/tests/` プレフィックスの依存を集める）で得る
6. `sb-cover:report` で HTML を生成
7. カバレッジ生データを集計してテキストサマリを出力

**計装対象の範囲に注意する。** 手順 2 が計装するのは `:cl-mcp` から ASDF 依存で到達可能な
ファイルだけである。テストからしか参照されない src ファイルがあれば計装されず、
レポートに現れない。**レポートに現れたファイル数が src の 59 ファイルと一致するかを
必ず突き合わせ、欠けたファイルは分類テーブルに理由付きで記録する。**
「レポートに載っていない」と「カバレッジ 0%」は別の事実であり、混同すると盲点を見落とす。

### 5.2 fasl キャッシュの隔離

計装済み fasl が通常の ASDF キャッシュに残ると、その後の開発ビルドや CI まで遅くなる。
計測実行の間だけ `ASDF_OUTPUT_TRANSLATIONS` で専用キャッシュに逃がす。

ワーカー子プロセスは親の環境変数を丸ごと引き継ぐため、この設定はワーカーにも伝播する。
結果としてワーカーも計装済み fasl を読んで遅くなるが、**ワーカー側のカバレッジデータは
元々捨てるので数値には影響しない**。副作用は「遅くなる」だけだと割り切る。

### 5.3 テキストサマリは HTML をパースしない

sb-cover は HTML しか出さないが、カバレッジの生データは SBCL 側が保持している。
そこから直接集計する。HTML パースは sb-cover の出力書式が変わると黙って壊れるためである。

ただし生データへのアクセスは SBCL の内部シンボルに触る。
**このアクセスはアダプタ関数 1 つに閉じ込め、期待する形でなければ 0% を返さず明示的にエラーにする。**
黙って 0% が並ぶレポートは「カバレッジがないのか計測が壊れたのか」を区別できず、最悪の失敗モードである。

サマリ形式（カバレッジ率の低い順、0% は別枠）:

```
src/http.lisp          41.2%   expr  89/216   branch 12/38
src/tcp.lisp           55.0%   expr 132/240   branch 21/44
---- 一度も実行されていないファイル ----
src/worker/main.lisp   (ワーカー専用 — scripts/coverage-scope.md 参照)
```

### 5.4 実行時間と、計装で落ちるテストの扱い

素の全スイートが 353 秒なので、計装で 2〜3 倍として **12〜18 分**を見込む。

計装で遅くなった結果 `pool-startup-latency-test` のような時間依存テストが落ちる可能性がある。
その場合、**閾値を緩める改造はしない。** 落ちたテストは「計測実行時の既知の除外」として
分類テーブルに記録し、本番の閾値は監査対象のまま残す。
計測の都合で本番の品質ゲートを下げるのは本末転倒である。

## 6. 部品 2: 分類テーブル `scripts/coverage-scope.md`

src の全 59 ファイルを次の 3 分類に振り分け、各行に理由を添える。

| 分類 | 意味 | 期待される扱い |
|------|------|---------------|
| 親で実行 | 親プロセス内で動くのでカバレッジが正しく出る | 数値をそのまま信じてよい |
| ワーカー専用 | ワーカー子プロセス内でのみ動く | カバレッジ 0% でも「未テスト」を意味しない |
| 計測不能 | 計装実行時に除外した、またはレポートに現れなかった | 除外理由を明記する。§5.1 の突き合わせで欠けたファイルはここに入る |

§2.3 の見立てでは「ワーカー専用」は `src/worker/` 配下に限られるが、
**この見立ての検証自体をタスクとする**。`src/worker/handlers.lisp` が
core モジュールへの薄いディスパッチャであることは確認済みだが、
core 側が親プロセスのテストからも呼ばれているかは未確認である。

## 7. 部品 3: 監査実行

### 7.1 監査エージェントに渡す入力

`comprehensive-test` スキルは各テスターに context brief を配る作りなので、そこに以下を載せる。

- ベースライン: 3,548 アサーション緑 / 353 秒
- カバレッジ表（低い順）と分類テーブル
- **既知の意図的な赤**（`rove-red` フィクスチャ、§2.1）— これを「バグ発見」と誤報告させないため

### 7.2 観点

| 観点 | 既存 Perspective pool との関係 |
|------|------------------------------|
| 障害回復・プロセス境界 | **該当なし。カスタム観点として prompt を書き起こす。** Error Handling が近いが、クラッシュ復帰・ゾンビプロセス・FD リーク・タイムアウトはプロセス境界固有である |
| 異常入力・境界値 | 既存の Edge Case Explorer をほぼそのまま使える |

### 7.3 実行環境の分離

`comprehensive-test` は動いている cl-mcp サーバ経由でツールを叩くため、監査対象は
**監査エージェント自身が繋がっているサーバそのもの**になる。ワーカーを kill する、
無限ループを投げる、巨大ペイロードを送るといったプローブは自分の足場を崩す。

プローブを 2 種類に分けて扱う。

| プローブ種別 | 実行先 | 根拠 |
|-------------|--------|------|
| ワーカーレベルの障害注入（kill、タイムアウト、クラッシュ復帰） | 通常のセッション経由でよい | セッション affinity によりテスターごとに別ワーカーである。**かつ「本当に分離されているか」自体が検証項目である** |
| 親プロセスを壊しうるプローブ（不正 JSON-RPC、巨大ペイロード、プロトコル違反） | `scripts/stdio_tcp_bridge.py` で別プロセスの cl-mcp を TCP で立て、そちらに対して行う | 親は全セッション共有であり、壊すと全テスターが道連れになる |

## 8. 部品 4: 統合レポート

構成:

1. **サマリ** — 全体カバレッジ率、緑/赤、所見件数（Critical / Major / Minor）
2. **カバレッジ表**（低い順）と盲点リスト
3. **所見** — 観点別、severity 順
4. **次にやるべきこと** — 優先度付き

各所見には再現手順に加えて、**カバレッジ上の位置づけ**を必ず付ける。

- 「テストが一度も通っていない領域だった」→ 対策はテスト追加
- 「テストはあるのに漏れた」→ 対策はテスト設計そのものの見直し

この対応付けが、単なる監査ではなく「計測を先に行う」構成を選んだ理由である。

severity の定義は `comprehensive-test` スキルの基準（Critical / Major / Minor）をそのまま使う。

## 9. 失敗モードと扱い

| 失敗モード | 扱い |
|-----------|------|
| 計測が途中で落ちた | **部分データでレポートを出さない。** 明示的に失敗させる。半端な数値は誤った安心を与える |
| SBCL 内部シンボル依存が壊れた | 明示的にエラーにする（§5.3）。0% を黙って返さない |
| 計装で時間依存テストが落ちた | 閾値を緩めず、除外として分類テーブルに記録する（§5.4） |
| 監査エージェントの偽陽性 | **コーディネータが 1 件ずつ再現確認してからレポートに載せる。** 再現しなかったものは削除せず「再現せず」として別枠に残す（環境依存の可能性があるため） |

## 10. 計測基盤自体の検証

計測スクリプトが嘘をつくと全てが無意味になるため、2 つの検算を入れる。

1. **既知の答えとの照合** — §2.2 のスモークで `src/utils/strings.lisp` は 21/21 (100%) だった。
   全スイート計測でも同じファイルが 100% のままかを確認する
2. **0% が正しく出ることの確認** — 一度も呼ばれない関数を一時的に追加し、
   それが 0% として現れることを確認する（確認後に取り除く）

## 11. スコープ外

意図的に含めないもの。

- **CI 統合とカバレッジ閾値ゲート** — 今回の目的は現状把握である。閾値は現状の数値を見てから決めるべきで、先に決めると恣意的になる
- **ワーカー子プロセス内のカバレッジ計測** — 起動経路への介入とデータマージが必要で脆い。盲点として明示する方を選んだ
- **セキュリティ境界と並行性・リソースの監査** — 今回の重点観点から外した。過去の監査記録に既知の指摘（環境変数のワーカーへの丸ごと引き渡し、バックトレースでのパス・ポート露出）があるが、本サイクルでは扱わない
- **ロバスト性テストの実装** — 所見リストの作成までが今回の範囲である。テスト追加は次のサイクルとする
- **macOS / 複数 SBCL バージョンでの検証** — CI で macOS は無効化されたままだが、本サイクルでは触らない

7. 統合レポートに、各所見のカバレッジ上の位置づけが付いている
